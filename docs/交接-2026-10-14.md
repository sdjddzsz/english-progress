### 9.2 ★ 分页排序键必须唯一（真 bug，已修）

`listBookWords` 原来用 `orderBy: 'orderInList'` 翻页。而 **`DEFAULT_LIST_SIZE = 50`**
⇒ 8296 行里 `orderInList` 只有 **166 个不同值**，重复率极高。
PostgREST 靠 `Range` 头 offset 翻页，**非唯一排序键下 Postgres 不保证跨页稳定**
（行重复出现 / 部分行永不出现）。改为按主键 `id` 排序（唯一）。
需要词频序的调用方自行排序 —— `pickBookWordSample` 本来就是这么做的。

### 9.3 答题音效（用户新需求，已做）

- 新模块 `src/audio/sfx.ts`：**Web Audio 实时合成**（零网络、零资源、零缓存依赖）——
  音效是反馈，不能像 TTS 那样依赖主轨/密钥/网关/缓存。
  答对 = A5→E6 上行（sine）；答错 = Eb4→Bb3 下行（triangle）。音量刻意压到 0.1，不盖住发音。
- `src/hooks/useSfx.ts`：统一入口，自动遵循设置开关。
- 设置页新增「答题音效」开关（`useSettingsStore.sfxEnabled`，默认开）。

**⚠ 接入范围（重要，已向用户说明）**：
拼写是**全书唯一有客观对错**的环节，所以对错音效只接在这里。
摸底 / 背词 / 听音选词 / 中译英都是**自评式**（`answer(l1: L1State)`，用户自己判断认不认识），
没有"答对/答错"的概念 —— 这是产品刻意设计，有 `tests/qa/antiSelfTest.test.ts` 硬约束钉死

若用户希望这些环节也有声音反馈，应加**中性"揭晓提示音"**（不带对错含义），而不是对错音效。

### 9.4 「今天声音机械感严重」的答案（非 bug，是引擎切换）

**不是音质变差，是引擎换了。**

- 主轨（DashScope 神经语音，自然音）需要 `status === 'active'` **且** 会话内存里有 API Key。
- `runtimeApiKey` 是**模块级变量、刷新即失**（架构 §8 #2 的有意设计，见 `hooks/useTTS.ts:19`）；
  只有用户在设置页勾选「跨刷新保留」时，key 才随 `apiKeyRef` 落库、启动时由 `bootRuntime()` 注入。
- ⇒ 昨天粘了 key 当场试听 = 主轨 = 自然音；今天刷新后 key 没了 = espeak 兜底 = 机械音。
- 顺带说明：**昨天"没声音"与今天"有声音但机械"是同一修复的两面** ——
  espeak 之前 `defaultVoice` 恒空、`speak()` 直接返回 null（静默），所以你只听到主轨；
  修好 `loadVoice` 后兜底轨能出声了，主轨一掉线就听得出机械音。

**已改进**：设置页试听提示现在**先分清「密钥不在会话里」与「密钥在但主轨请求失败」**
（两者现象一样、修法完全不同）；原先只列 CORS/Key/端点三条，漏了最常见的原因。

**给用户的一句话**：想一直听自然音 → 设置页勾选「跨刷新保留」再保存一次。

### 9.5 ★ 测试桩抓出的真缺陷（值得记）

`tests/helpers/mockDb.ts` 的 `count` 返回 `rows.length`（**未过滤的全表行数**），
而 PostgREST `count=exact` 的语义是 **WHERE 之后、分页之前** 的总数。
⇒ `count(filters)` 在测试里永远返回全表数，「按 tier 计数」「按 bookId 计数」这类调用
在测试中看起来都对、实际全错。由本轮新增的 `countBookWordsByTier` 用例抓出，已修。

**教训（与 10-13「mockDb 兜底 id」同一类）**：桩不只是"能跑就行"，
它必须**忠实复现服务端语义**，否则测试会给出虚假的安全感。

## 十二、★ TTS 主轨（端点 / 密钥）怎么填 —— 用户 2026-10-14 问「一刷新就没了」

### 12.1 正确填法（DashScope）

设置页 TTS 卡片，逐项：

| 字段 | 填什么 | 留空会怎样 |
|---|---|---|
| provider | `dashscope`（默认） | —— |
| 发音人 voice | 留空即可 | 用默认 `longanyang` |
| 模型 model | 留空即可 | 用默认 `cosyvoice-v3-flash` |
| 端点 endpoint | 留空即可 | 用默认 `https://dashscope.aliyuncs.com/api/v1/services/audio/tts/SpeechSynthesizer` |
| **API Key** | 粘贴 DashScope 的 key（`sk-` 开头） | **主轨必然不通，只能听机械音** |
| **跨刷新保留** | **必须勾选** | 不勾 = key 只在会话内存，**刷新即失** |

保存后**立刻点「试听」验证**：显示「主轨（神经语音）发音成功」且声音自然才算成功；
若显示「走的是 espeak 兜底（机械音）—— 会话里没有 API Key」，说明保存没生效。

### 12.2 「一刷新就没了」的机制

`runtimeApiKey` 是 `hooks/useTTS.ts` 里的**模块级变量**，刷新必然重置（架构 §8 #2 的有意设计）。
只有勾了「跨刷新保留」，`handleSaveTTS` 才会把 `apiKeyRef='runtimeApiKey'` + `runtimeApiKey=<key>`
写进云端 `tts_provider_configs`；启动时 `bootRuntime()` 按 `apiKeyRef` 读出并注入内存。

⇒ **不勾选，刷新后 key 必丢**，这不是 bug，是设计。想要持久化就勾。

### 12.3 云端列已确认存在（别再怀疑表结构）

- 2026-10-12 已执行 `ALTER TABLE tts_provider_configs ADD COLUMN "runtimeApiKey" text`（返回 `[]`，即列已存在）。
- 2026-10-13 复核过 `words` / `tts_provider_configs` / `pronunciation_logs` 三表列与代码类型一致。
⇒ **列不是失败原因**，失败原因只可能是没勾选或保存时报错被忽略。

### 12.4 ⚠ 已知 UX 坑（待修，用户可能被它误导）

设置页密钥框的初值是 `useState(peekRuntimeTTSApiKey())`，**只在组件 mount 时求值一次**；
而 `bootRuntime()` 是异步的（在 `useAppStore` 的 bootstrap 里）。若它在设置页 mount 之后才完成，
**密钥框会显示为空** —— 但发音用的模块变量其实已经注入成功了。

⇒ 用户会看到「框是空的」而以为密钥丢了，实际上发音可能正常。
**修法**：加载 `ttsConfig` 后，若 `cfg.runtimeApiKey` 有值就回填输入框与勾选状态
（`SettingsPage.tsx` 已有 `setPersistKey(Boolean(cfg.runtimeApiKey))`，只差 `setApiKey`）。

## 十三、★「昨天试听是自然音、今天怎么点都是机械音」—— 两个叠加的真 bug（已修 `badf94e`）

用户 10-13 试听成功（主轨/自然音），10-14 同一配置却走 espeak 兜底，且红框提示
「密钥在会话里，但主轨请求没通」。**直接查云端 `tts_provider_configs` 定位**（别再让用户自己 F12）。

### 13.1 查到的事实

| 字段 | 值 | 说明 |
|---|---|---|
| `status` | **`error`** | ★ 主因 |
| `voice` | **`1443733504@qq.com`** | 用户邮箱 —— 历史脏值 |
| `model` / `endpoint` | `cosyvoice-v3-flash` / DashScope 国际站 | 正常 |
| `runtimeApiKey` | 长度 116，`apiKeyRef='runtimeApiKey'` | key 确实落库了 |

⇒ **key 没问题、端点没问题**，是配置被写坏了 + 主轨被自己关掉了。

### 13.2 Bug 1：死锁（主因）

- `SettingsPage.tsx` 试听回写：`status: engine === 'neural_tts' ? 'active' : engine ? 'error' : ...`
- `orchestrator.ts:120`：`if (cfg && cfg.config.status === 'active' && cfg.apiKey)` 才发主轨请求
- ⇒ **一次试听失败就把 status 置 error，主轨从此被永久跳过；之后再点试听仍是 espeak，
  请求根本没发出去，用户没有任何自愈手段**（除非重新保存）。

这就是「昨天通、今天不通」的机制：昨天成功时 status=active；后来某次失败置成 error，从此锁死。
**红框文案「主轨请求没通」也有误导** —— 实际是请求压根没发。

### 13.3 Bug 2：脏数据 + 显示/保存不一致

- 云端 `voice` 列存着用户邮箱（历史脏值，来源已不可考；`voice` 是下拉，用户填不进去）
- 下拉 `value={effectiveVoice}`（已按模型校正、显示正常），但 `handleSaveTTS` 存的是 `voice` state
- ⇒ **界面看着正常、存进去是非法音色名 → 主轨 400 → 试听失败 → 触发 Bug 1 锁死**
- 脏值传播链：localStorage 脏 `ttsVoice` 非空时，`if (cfg.voice && !voice) setVoice(...)` 不覆盖
  ⇒ 每次保存把脏值反复写回云端。

### 13.4 修复内容（`badf94e`）

1. 试听回写**只在成功时置 active，失败绝不动 status**（配置有问题时红框提示 + 用户重保存就够了）
2. `handleSaveTTS` 改存 `effectiveVoice`（与下拉显示一致）
3. 加载云端配置时**无条件覆盖**本地 `voice`（断掉脏值传播链）

### 13.5 数据侧（已直接修好，用户刷新即生效）

```sql
UPDATE tts_provider_configs SET voice = 'longanyang', status = 'active';
```

**教训**：这类"昨天好今天坏"的故障，**第一反应应该是查云端配置表**（`tts_provider_configs` 的
status / voice / endpoint / apiKeyRef / runtimeApiKey 五个字段一眼看清），而不是让用户去 F12。
编排器还会把失败原因写进 `pronunciation_logs.error`，也是可查的。

## 十四、★「所有发音人同一个音」+「手机机械音刷新也没用」—— 缓存两个真 bug（已修 `3cae736`）

用户 2026-10-14 报：① 换发音人听起来都是同一个音；② 电脑正常、手机机械音且刷新也没用。

### 14.1 Bug A：缓存 key 与发音人/模型无关

`cacheKey` 原来是 `text|mode|ipa|arpabet|voice`，而**所有页面调 `speak()` 都不传 voice**
（`SpellingPage` / `StudyPage` / `CnToEnPage` / `SearchPage` 全部只传 text/ipa/arpabet/mode）
⇒ `req.voice` 恒为 undefined ⇒ **key 与发音人、模型完全无关**。

主轨请求用的是 `ctx.config.voice`（`dashscopeProvider.ts:106,294`，合成时是对的），
所以现象是"音色切了、听起来没变"——**不是音色没生效，是缓存里还是旧音频**。

### 14.2 Bug B：兜底的机械音被写进了缓存（手机刷不掉的根因）

```js
} catch (err) {
  const fb = await espeak.synthesize(req);
  await deps.cache.put(key, fb.audio, fb.engine);   // ← 就是这一行
```

主轨失败多是**瞬时**的（网络抖动 / CORS / 密钥未注入）。一旦把机械音 put 进 CacheStorage，
即使主轨随后恢复，同一个词也**永远命中那份机械音** —— 缓存在 CacheStorage，**刷新清不掉**。

⇒ 电脑正常、手机机械音：**两台设备的 CacheStorage 是独立的**，
电脑里存的是主轨音频，手机里存的是早先某次失败时写入的 espeak 音频。

### 14.3 修复

1. `cacheKey` 升 **v2**：并入 voice + model（双来源：调用方显式传入优先，其次 `req.voice`），
   并加 `v2` 前缀 ⇒ 线上已沉淀的旧格式缓存（含误存的机械音）**自然失效、不迁移**。
   **这一步同时解决了用户手机上已有的脏缓存，无需手动清。**
2. 兜底音频**绝不入缓存**（主轨失败分支 + 未配置分支两处都去掉 put）。
3. `getAudio` 改为**先读配置再查缓存**（key 需要 voice/model；多一次云端读仍在 <800ms 内）。

### 14.4 测试

- 更新 3 条钉旧行为的用例（key 段数 5→7、兜底入缓存→不入缓存）
- 新增回归锚点「换发音人 / 换模型必须换 key」
- 基线：**34 files / 424 tests 全绿**

### 14.5 顺带回答（用户原问）

- **每个单词会缓存**：缓存在浏览器 CacheStorage（`tts-audio`），key = `v2|text|mode|ipa|arpabet|voice|model`，
  命中就直接播、不重新合成（这是有意的 <800ms 体验路径）；不主动失效，按 LRU 预算淘汰。
- **换音色/换模型会换 key** ⇒ 会重新合成；不换则命中缓存。
