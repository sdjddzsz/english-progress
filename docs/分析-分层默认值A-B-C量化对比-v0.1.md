## 零、先纠正一处事实（很重要）

`validate.ts` / `planRounds` 的窗口天数：

```
T = diffDays(deadline, start) = 2026-12-05 − 2026-10-13 = 53 天   （不是 54）
maxDailyHits = floor(dailyBudgetMin × 60 / avgHitSec) = floor(60×60/12) = 300 hit/天
```

- 校验用53 天（`validatePlan.windowDays`）；
- 物理单轮下限 `floorDays = ceil(W_t / maxDailyHits)`；
- **关键推论**：任一方案的真实约束不是"分钟够不够"，而是「**层内轮次窗口能否塞进 53 天**」。

## 一、三方案量化对比（60min/天，avgHitSec=12s，推荐档 {T1:2,T2:2,T3:3,T4:3}）

| 指标 | **A. 全 T4** | **B. 现行先验**（1352 T2 / 1893 T3 / 2162 T4） | **C. 全T4+摸底回填** |
|---|---|---|---|
| 层分布 | T4:5407 | T2:1352 / T3:1893 / T4:2162（=词频 25%/35%/40%） | 取决于抽样结果，见 §三 |
| 总 hit | **16221** = 5407×3 | **14869** = 1352×2+1893×3+2162×3 | 13411 ~ 15681（随抽样认识率 50%~95%） |
| 日均 hit | **307** = ⌈16221/53⌉ | **281** = ⌈14869/53⌉ | 254 ~ 296 |
| 日均分钟 | **61.4** = 307×12/60 | **56.2** = 281×12/60 | 50.8 ~ 59.2 |
| 相对60min 裕度 | **−2.3%（超支）** | +6.3% | +1.3% ~ +15.3% |
| 推荐档校验 | **不通过**（`critical=true`，落临界带） | **通过** | 通过 |
| 单轮物理下限 | floorDays = ⌈5407/300⌉ = **19 天** | T2:⌈1352/300⌉=5 / T3:7 / T4:8 | 视分布 |
| 实际轮窗 | [19,19,19] = **57 天 > 53** | T2:[27,26] / T3:[18,18,17] / T4:[18,18,17] | 视分布 |
| **预计完成日** | **2026-12-08** | **2026-12-04** | 2026-12-04 |
| 能否 12-05 前完成 | **不能，逾期 3 天**（且这 3 天直接吃掉冲刺周） | **能**（富余 1 天） | 能 |

**算式（可复核）**
```
A: 5407×3 = 16221；⌈16221/53⌉ = 307；307×12/60 = 61.4 > 60 → 不通过
   轮窗：T=53, R=3 → base=⌊53/3⌋=17, rem=2 → [18,18,17]；再取 max(·, ⌈5407/300⌉=19) → [19,19,19]
   起 10-13 + 57 天 − 1 = 12-08
B: 1352×2 + 1893×3 + 2162×3 = 2704+5679+6486 = 14869；⌈14869/53⌉ = 281；281×12/60 = 56.2 ≤ 60 → 通过
   T4: R=3 → [18,18,17]（floorDays=8 不触发）；T2: R=2 → base=26,rem=1 → [27,26]
   T4 收尾：10-13 + 53 − 1 = 12-04
```
>注：`dailyMinutes` 与 `maxDailyHits` 是两个独立判据。A 方案两者**同时**触界（分钟超 2.3%、轮窗超 4 天），所以"提预算到 62min"能救校验但救不了逾期（见 §二）。

## 二、直接回答：全 T4 会不会把推荐档压垮？

**会，但只差2.3%，且有两条便宜的解法。**

**证据 1：分钟口径只超 2.3%**
```
61.4 − 60 = 1.4 分钟/天 → 相对超支 1.4/60 = 2.3%
落在 CRITICAL_MARGIN_RATIO = 0.05 内 → validate 返回 critical=true（临界，不是严重超载）
```

**证据 2：真正的硬伤是轮次窗口超 4 天**
```
floorDays = ⌈5407 / 300⌉ = 19 天/轮（每轮都要覆盖 5407 词，日上限 300 hit）
3 轮 × 19 = 57 天 > 53 天 → 结构性逾期 4 天
注意：这是"每轮都要把 5407 词过一遍"的必然结果，与分层无关
```

### 解法 1：提预算（最小改动）

| 预算 | maxDailyHits | floorDays | 轮窗 | 完成日 | 逾期 | 校验 |
|---|---|---|---|---|---|---|
| 60（现状） | 300 | 19 | [19,19,19] | 12-08 | **+3** | ✗ |
| **62** | 310 | 18 | [18,18,18] | **12-05** | **0** | ✓ |
| **65** | 325 | 17 | [18,18,17] | **12-04** | −1 | ✓ |
| 70 | 350 | 16 | [18,18,17] | 12-04 | −1 | ✓ |
| 120（上限） | 600 | 10 | [18,18,17] | 12-04 | −1 | ✓ |

> **最小可行预算 = 62 分钟/天**（正好卡在 12-05 完成，不逾期）。**建议 65 分钟**，留 1 天缓冲且仍在 `DAILY_BUDGET_MIN_RANGE=[30,120]` 内。

### 解法 2：降轮次（不动预算）

| 轮次 | 总 hit | 日均 hit | 日均分钟 | 轮窗 | 完成日 | 校验 |
|---|---|---|---|---|---|---|
| T4×1 | 5407 | 103 | 20.6 | [53] | 12-04 | ✓（过松） |
| **T4×2** | **10814** | **205** | **41.0** | [27,26] | **12-04** | ✓（富余 27%） |
| T4×3 | 16221 | 307 | 61.4 | [19,19,19] | 12-08 | ✗ |

> T4×2 = 保底档口径，日均 41 分钟，**比现在（B 的 56.2）还宽松**，但代价是 5407 词只过 2 轮。

### 关键风险：avgHitSec 是估计值，不是实测值

PRD 自己标注 T4 生词**可能 20s+**。若T4 真实耗时是 20s 而非 12s：

| avgHitSec | A(T4×3) | A(T4×2) | B(现行先验) |
|---|---|---|---|
| 12s（默认估计） | 61.4min ✗ 逾期3天 | 41.0 ✓ | 56.2 ✓ |
| 15s | 76.8 ✗ 逾期15天 | 51.2 ✓ | 70.2 ✗ |
| 18s | 92.1 ✗ 逾期30天 | 61.5 ✗ 逾期2天 | 84.3 ✗ |
| **20s** | **102.3 ✗ 逾期39天** | **68.3 ✗ 逾期8天** | **93.7 ✗ 逾期39天** |
| 25s | 127.9 ✗ 逾期60天 | 85.4 ✗ 逾期22天 | 117.1 ✗ |

> **这是全篇最重要的一张表**：在 20s 情形下 **A 和 B 一起崩**（B 也要 120min/天才勉强不逾期）。所以
> **"选A还是B"在 20s 情形下不是A/B之争，而是两者都要降轮次或加预算。**
> 反过来说：在 12s 情形下 A 只差 2.3%，B 的"优势"也只有 6.3%——**两者差距 8.6 个百分点，都是估计参数的噪声量级**。

## 三、C 方案：抽样率 5.5% 下，它其实≈ B（真判断）

### 3.1 摸底能覆盖多少词

```
PLACEMENT_MAX_WORDS = 300（constants.ts:80）
抽样覆盖率 = 300 / 5407 = 5.55%
未覆盖 = 5107 词 = 94.45% → 零测评证据
```

**代码事实（我核实了，不是转述）**：`PlacementPage.tsx:141` 的
`estimateTierAssignments(responses)` **只对被点答的 ≤300 词产出 assignments**，
经`recompute_word_tiers` 写入。也就是说 **C 方案"回填未抽到的 5107 词"这件事，今天的代码根本不存在**——
摸底只改被抽中词的层，其余 5107 词保持初始值。C 要额外开发"按带认识率外推回填"的逻辑。

### 3.2 就算实现了，精度如何？分带抽样误差实算

抽样按 `BAND_RATIOS = [0.4,0.3,0.2,0.1]` 分 4 带（每带 ⌈5407/4⌉ = **1352 词**），配额 **120 / 90 / 60 / 30**：

| 带 | 抽到词数 | 带内词量 | 若真实认识率 50%，95% CI | 折算全带不确定量 |
|---|---|---|---|---|
| 带1（最高频） | 120 | 1352 | ±8.9% | **±121 词** |
| 带2 | 90 | 1352 | ±10.3% | **±140 词** |
| 带3 | 60 | 1352 | ±12.7% | **±171 词** |
| 带4（最低频） | **30** | 1352 | **±17.9%** | **±242 词** |

```
SE = sqrt(p(1−p)/n)；95%CI = ±1.96×SE；外推不确定量 = CI × 1352
带4只抽 30 词 → 认识率的 95% 置信区间宽达 ±17.9pp（认识率真值可能是 32% 也可能是 68%）
```

### 3.3 直说结论

**C 在 5.5% 抽样率下与 B 实质等价，而且比 B 更贵。** 三条理由：

1. **回填的输入只有 300 个数据点，却要决定 5407 词的层归属。** 外推误差 ±121~242 词/带，
   而 B 的先验误差是多少？无从量化——但 B 的"高频=更熟"这个假设在六级这种标准化考试词表上，
   与真实认知结构的偏离通常是**单调、平滑、量级为几百词**；C 的抽样噪声是**随机、无结构、量级 ±121~242 词/带**。
   **两者误差量级相同，C 还额外引入了随机性。**
2. **C 的产出不稳定、不可复现。** 抽到哪 300 词由 `hashString` 决定（确定性但与用户能力无关）；
   换一天抽、认识率波动 10pp，回填结果就变几百词。用户会看到"同样的词书，分层结果不一样"——
   这直接违反产品哲学第1 条（进度必须由我掌控、不由算法掌控）。
3. **C 要多开发一条"按带认识率外推回填"的链路**（带级认识率 → 5107 词的层映射 + 置信区间提示 + 幂等重跑），
   而收益仅是把B 的猜测换成另一个猜测。

**C 唯一优于 B 的场景**：用户实际能力与词频**强相关**（高频带认识率 95%+、低频带 30%−）。
即便如此，抽样噪声仍在±121~242 词/带——**不足以支撑"分层"这种颗粒度的决策**。

**⇒ C 不推荐。要么 A（诚实：全部当生词），要么 B（保留先验），不要 C。**

## 四、推荐：A，但必须配一个"诚实标签"和两条参数动作

### 4.1 推荐 A 的理由（按权重排序）

| # | 理由 | 量化支撑 |
|---|---|---|
| 1 | **回答了用户的真问题** | 用户问的是"凭什么分出熟词"，A 的答案是"不凭什么——未测评前一律当生词"，逻辑自洽；B 无法回答 |
| 2 | **代价可量化且很小** | A vs B 差**1352 hit = 25.5hit/天 = 5.1 分钟/天**（61.4 vs 56.2）。这是能一句话说清、能被用户拍板的量级 |
| 3 | **A 的误差方向是安全的** | 把熟词当生词 → 多复习（浪费但不漏）；把生词当熟词 → 少复习（**漏掉=考试丢分**）。PRD §4.3 的校准逻辑本身写明"宁严勿松"（`calibration.ts:24`：`downgrade`优先于`instantStreak`） |
| 4 | **B 的 25/35/40 是拍脑袋常数** | 代码里没有任何依据（`seedBootstrap.ts:187` 硬编码 0.25/0.6），而 `constants.ts` 其他默认值都有注释说明来源 |
| 5 | **摸底+ 每日校准会自动修正 A** | `calibration.ts` 前 14 天按近 2 日反馈调层：连续 2 次秒认 → 上移一层。实测数据 3~5 天内就会把真熟词升上去 |

### 4.2 A 必须同时做的三件事（缺一不可）

| # | 动作 | 参数 | 依据 |
|---|---|---|---|
| 1 | **日预算 60 → 65 分钟** | `DEFAULT_DAILY_BUDGET_MIN` | §二解法1：62min 是卡线，65min 留 1 天缓冲；仍在 [30,120] 区间内 |
| 2 | **首轮排期按 T4×2 起步，达标后升 3 轮** | 保底档全 2 轮 → 第 1 周后按实测升 | T4×2 日均 41 分钟（富余 27%），给 `avgHitSec` 估计误差留出兑现空间 |
| 3 | **UI 标注"未测评"** | 词书页/首页 | 现在的 `TIER_LABEL` 直接显示"生词/熟词"，用户会误以为系统知道。需区分「实测层」与「默认层」 |

### 4.3 强烈建议（不属A/B/C，但影响可行性）

**实测 `avgHitSec`。** 这是全篇最大的不确定性来源：
- 若实测 ≈ 12s：A（65min + T4×3）成立，B 的"优势"仅 6.3%；
- 若实测 ≈ 20s：**A 和 B 都不成立**，必须降到 T4×2 且预算提到 ≥70 分钟，否则全盘崩。

实测方法（不改代码）：连续 3 天记录 `hits_today` 表的实际 (done 数, 用时)，
取 `总秒数 / done 数`。这是把"估计"变成"实测"的唯一途径。

## 五、实现代价：改默认值 ≠ 改代码就生效

### 5.1 现状事实（已核实）

- `book_words.tier` 已在云端写入 **5407 行**（`seedBootstrap.ts:206`）。
- `seedBootstrap` **幂等**：`upsertBookWords` 冲突跳过；且有**终局身份集合校验**（`verify()` 判期望 id ⊆ 云端 id）——
  重跑不会把已有 tier 改回去，**只会补缺失行**。
- `recompute_word_tiers`（`catalog.ts:48`）：变更 >10%（`TIER_RECALIBRATION_CONFIRM_RATIO = 0.1`）走 Confirm 提案。
-摸底 `PlacementPage` 只写≤300 词（见§3.1）。

### 5.2 三条路径对比

| 路径 | 做法 | 用户代价 | 风险 | 评价 |
|---|---|---|---|---|
| **① 一次性 UPDATE** | `UPDATE book_words SET tier=4 WHERE book_id='book_cet6_full' AND tier IN (2,3)`<br/>影响 3245 行 | **5 秒，零感知**（若配 loading 提示）；分层立刻生效 | 丢失原分层信息（**不可回滚**，建议先备份 tier 到 `tier_snapshots`） | ✅ **推荐** |
| ② 重跑初始化 | 改 `seedBootstrap.ts:187` 为全 T4 后重跑 | 无实际效果——幂等 upsert **不会覆盖已有行**（§5.1） | 误以为改了就生效，实际没改 | ❌ **无效** |
| ③ 重跑摸底 | 走PlacementPage | 3~5 分钟；但**只改 300 词**，剩 5107 词不变 → 得到"A 与 B 的混合体"，比现状更混乱 | 分层不一致 | ❌ **不解决问题** |

**结论：走路径 ①。** 补充要求：
1. 执行前把现有 3245 行的 (bookWordId, tier) 备份进 `tier_snapshots`（表已存在，`configRepo.ts:116saveTierSnapshot`），
   保留 `responses`/`computedTiers` 可回溯；
2. 若走 `recompute_word_tiers`工具通道而非裸 SQL，3245/5407 = 60% > 10% 阈值 → 会生成 Confirm 提案，
   符合产品哲学（重大变更需用户确认），**这是优点不是麻烦**；
3. 执行后**必须重算并让用户确认计划**：`planRounds` 的 `floorDays` 会从 5/7/8 跳到 19，
   轮次窗口重排 → 已有 `hits`（按旧窗口排的）会变孤儿，必须走 `overdue.ts` 的重排路径，不能只改 tier 就完事。
